## ① 卡在哪一句需求

工作包 024 的**紅線**（§B 路由）與**測試第 4 項**都要求：

> `GET /index.html`、`GET /static/index.html`、`GET //`、`GET /../src/server.py`
> ⇒ **全部 `404`**。

同時工作包契約（§B(2)）又規定路由只能照字面寫：

```python
if urlparse(self.path).path == "/":
    self._get_index()
```

實測結果（Python 3.12，`/usr/lib/python3.12`）：
- `/index.html`、`/static/index.html`、`/../src/server.py` → 404（符合）
- **`GET //` → 200**（不符）

根因不是我們的比對邏輯，是 **stdlib**：`BaseHTTPRequestHandler.parse_request()`
內建 gh-87389 修正（open redirect 防護），任何以 `//` 開頭的路徑在進 handler 之前就被
改成 `'/' + self.path.lstrip('/')`——`//` 到我們手上時 `self.path` **已經是 `/`**，
`urlparse(...).path == "/"` 自然命中。原始 requestline 保留在 `self.requestline`
（`"GET // HTTP/1.1"`），但契約沒有要我們看它。

因此「照契約字面寫」＋「`//` 回 404」兩者在這個 Python 版本上**無法同時成立**。

## ② 我想到的所有解讀

1. **接受 `//` → 200（放寬測試 4，契約一字不改）**：stdlib 自己把 `//` 正規化成 `/`
   是官方 open-redirect 防護，行為上是「請求根目錄」不是「路徑→檔案對映」；紅線要擋的
   「長出路徑到檔案的對映」完全沒被突破，`//` 只是拿到同一份靜態頁，無安全意義。
   測試 4 改為只測另外三條路徑，並註明 `//` 被 stdlib 正規化。
2. **加一條 raw requestline 守門（契約多加一行）**：在 GET 分支加
   `and self.requestline.split()[1] == "/"`，讓 `//` 回 404。偏離契約「照字面實作、
   不要多做」，且多出「requestline 是第 3 版 HTTP/0.9 請求時沒法 split」等邊界。
3. **換用非 3.12 的直譯器跑測試**：本機只有這個 Python，不實際。
