# 工作包 010：stdin 探測腳本

## 為什麼要做這件事

`SPEC.md` §3.1 決定「每輪重送完整逐字稿」，§5 又訂了輪數上限 5、單次發言
`max_chars` 8000。把逐字稿當成 argv 參數傳給 CLI 時，這三者互相矛盾——
Linux 的 `MAX_ARG_STRLEN` 上限約 131,072 **位元組**，而：

- 中文一字 3 bytes ⇒ 8000 字的發言 = 24,000 bytes ⇒ 累積 6 篇就爆，**第 2 輪就死**
- 英文 1 字元 1 byte ⇒ 累積 17 篇才爆，**撐不到第 4 輪結束**

若四家 CLI 能從 **stdin** 接收長 prompt，這個天花板就不存在，§3.1 的設計得以保留。
本工作包要產出的就是回答這個問題的探測工具。

⚠️ 附帶已知缺陷（**本工作包不要修，另包處理**）：`base.py` 的
`MAX_ARG_CHARS = 100000` 以 `len(prompt)` 比對，算的是字元不是位元組，
對中文完全失效。不要順手動它。

---

## ⚠️ 邊界：你不可以真的呼叫任何 CLI

`AGENTS.md`「對本專案特別要求」訂明真實 CLI 呼叫由主對話人工執行，因為那會消耗
Frank 的真實額度。**你要交付的是腳本本身，不是探測結果。**

- **不要**執行 `claude` / `codex` / `gemini` / `opencode` 任何一個。
- 交付說明中，探測結果一欄一律寫「未驗證（依規定由主對話執行）」。
- 但腳本的**非 CLI 邏輯你必須驗證**，做法見下方「驗收條件」——用假的 CLI stub 驗，
  不花任何額度。這部分沒驗證就交付視為不合格。

---

## 交付物

單一檔案：`dispatch/tmp/probe_stdin.sh`（可執行）。該目錄未版控，屬拋棄式工具，
不要為它加測試檔、不要改動 `src/` 或 `tests/` 任何檔案。

## 腳本要回答的問題

對四家 CLI 各自判定三件事：

1. **它會不會讀取管道餵入的 stdin？**
2. **餵了 stdin 之後會不會卡住？**
3. **stdin 能不能承載遠超過 argv 上限的長內容？**

### 判定方法（必須照這個設計，不要自創）

用一個**標記字串**來證明 stdin 真的被讀進去了，而不是被忽略：

- stdin 內容結尾放一句指示，要求模型原樣輸出標記 `STDIN-OK-7Q4X`
- argv 那一側只放中性指示（例如「請依照輸入的內容回答」），**標記絕不可出現在 argv**
- 若輸出含標記 ⇒ stdin 被讀取；不含 ⇒ 未被讀取

這個設計的重點是**對照性**：argv 沒有標記，所以標記只可能來自 stdin。
不要改成「問模型你有沒有收到 stdin」——那是問模型的自述，不算證據。

### 兩個階段

| 階段 | stdin 內容 | 要證明的事 |
|---|---|---|
| A · 短 | 只有那句標記指示（數十字元） | stdin 到底通不通 |
| B · 長 | 約 150 KB 填充文字 + 結尾同一句標記指示 | 長內容能否突破 argv 上限 |

階段 B 只對階段 A 通過的 CLI 執行（A 都不通，B 沒有意義）。
填充文字請用**中文字元**產生，因為真實逐字稿是中文，這樣才測到位元組上限。

### 四家的呼叫方式

基底指令照 `SPEC.md` §4.1 表格，**唯一的改動是 stdin 從 `/dev/null` 改為管道餵入**。
`opencode` 這一支用 `-m opencode/deepseek-v4-flash-free`（免費），且探測不需要
`--agent advisor`，可省略。

⚠️ `gemini` 遇 503 會自行重試退避，單次可能耗時 100～120 秒 ⇒ 逾時一律設 **180 秒**
（`SPEC.md` §5 邊界 4 的理由相同）。逾時要能強制終止，不可讓腳本掛死。

### 輸出格式

腳本執行完印一張表，每個 CLI 一列，至少含：

`CLI · 階段 · 退出碼 · 耗時秒 · 標記是否出現 · 判定 · stderr 首要錯誤行`

判定欄位只用這四個值之一，讓人一眼看懂、不必自己解讀：
`stdin 可用` / `stdin 被忽略` / `卡住逾時` / `呼叫失敗`

原始輸出請各自留檔到 `dispatch/tmp/`（檔名含 CLI 與階段），供主對話事後複核——
表格是結論，原始檔是證據，兩者都要有。

## 驗收條件（你必須自己做到，且要貼出真實輸出）

1. `bash -n dispatch/tmp/probe_stdin.sh` 語法檢查通過。
2. **用假 CLI stub 驗證腳本邏輯**：另外寫一個暫時的 stub 腳本（例如
   `dispatch/tmp/fake_cli.sh`），行為是把 stdin 原樣印到 stdout。把探測腳本指向
   這個 stub 執行，證明：
   - stub 會讀 stdin 的情況下，判定欄正確給出 `stdin 可用`
   - 把 stub 改成**忽略 stdin**（只印固定字串）時，判定欄正確變成 `stdin 被忽略`
   - 兩種情況都要貼出實際印出的表格
   ⚠️ 這一條是本包最重要的驗收項。**只證明「有標記時判對」不夠，必須同時證明
   「沒標記時判錯不會發生」**——單向的測試無法分辨「邏輯正確」與「永遠回傳可用」。
3. 階段 B 的 150 KB 填充確實是中文（貼出 `wc -c` 與字元數，兩者應相差約 3 倍）。
4. 逾時機制可驗證：用一個會 sleep 的 stub，證明腳本會在設定秒數後終止它並判為
   `卡住逾時`，而不是自己掛住。

## 交付說明要寫的事

- 上述四項驗收各自的**真實輸出**（不是描述，是貼出來的內容）。
- 明確一句：「四家真實 CLI 未呼叫，探測結果未驗證」。
- 任何你做了但不確定的判斷，照 `AGENTS.md` 標為未驗證。

## 卡關就停手

需求有歧義時不要猜，照 `AGENTS.md` 寫 `dispatch/BLOCKED.md` 並結束該輪。
